# Техническое задание: Task Carousel

## 1. Цель

Разработать мобильное веб-приложение для последовательной работы над несколькими параллельными задачами.

Пользователь видит только одну текущую задачу, фиксирует сделанный прогресс и переходит к следующей. После последней активной задачи карусель возвращается к первой.

Главный сценарий:

1. Пользователь добавил четыре задачи.
2. Открывает первую задачу.
3. Немного работает над ней.
4. Записывает, что сделал и где остановился.
5. Нажимает **«Записать и дальше»**.
6. Открывается следующая задача.
7. После четвёртой снова открывается первая.
8. Завершённые задачи автоматически исключаются из карусели.

Приложение должно минимизировать необходимость выбирать следующую задачу и не перегружать пользователя общим списком.

## 2. Технологический стек

Использовать:

* TypeScript;
* React;
* Vite;
* Cloudflare Vite Plugin;
* Cloudflare Worker для API и раздачи frontend;
* Cloudflare D1 в качестве базы данных;
* Cloudflare Access для авторизации;
* CSS Modules или обычный CSS с CSS variables;
* Vitest для unit-тестов;
* Playwright для основных end-to-end сценариев;
* пакетный менеджер `pnpm`.

Frontend и API должны разворачиваться как одно Cloudflare Workers-приложение.

Cloudflare официально поддерживает full-stack React + Vite приложения с Worker API. На бесплатном тарифе доступны 100 000 Worker-запросов в сутки, статические файлы обслуживаются бесплатно, а бесплатная D1-база ограничена 500 МБ, чего достаточно для такого приложения.

Название проекта и Worker:

```text
task-carousel
```

## 3. Авторизация

Не реализовывать собственные пароли, регистрацию и восстановление пароля.

Использовать Cloudflare Access:

* приложение полностью закрыто Cloudflare Access;
* вход по одноразовому коду, отправленному на разрешённый email;
* список разрешённых пользователей задаётся в Access Policy;
* Worker обязан проверять подпись JWT из заголовка `Cf-Access-Jwt-Assertion`;
* идентификатором пользователя внутри приложения служит нормализованный email из проверенного JWT;
* все запросы к API должны выполняться только от авторизованного пользователя;
* пользователь видит свой email в меню профиля;
* кнопка **«Выйти»** отправляет пользователя на:

```text
/cdn-cgi/access/logout
```

Cloudflare Access должен быть включён и для production URL, и для preview URLs.

## 4. Основные экраны

### 4.1. Экран карусели

Это главный экран приложения.

На экране одновременно отображается только одна активная задача.

Состав экрана:

* название приложения;
* индикатор позиции: `2 из 4`;
* название текущей задачи;
* описание задачи, если оно заполнено;
* последняя запись прогресса;
* время последней записи;
* поле **«Что сделал и где остановился?»**;
* основная кнопка **«Записать и дальше»**;
* кнопка **«Пропустить»**;
* кнопка **«Готово»**;
* переход к истории прогресса;
* кнопка добавления задачи;
* меню пользователя.

Переход между задачами:

* свайп влево — следующая задача;
* свайп вправо — предыдущая задача;
* на desktop также доступны кнопки со стрелками;
* клавиши `ArrowLeft` и `ArrowRight` переключают задачи, если фокус не находится в текстовом поле;
* `Ctrl+Enter` и `Cmd+Enter` выполняют действие **«Записать и дальше»**;
* карусель циклическая;
* после последней задачи открывается первая;
* перед первой задачей находится последняя.

Свайп не должен срабатывать при выделении текста или горизонтальном движении внутри текстового поля.

### 4.2. Экран всех задач

Содержит две вкладки:

* **Активные**;
* **Выполненные**.

Для активной задачи показывать:

* название;
* короткое описание;
* дату последнего прогресса;
* число записей прогресса;
* действия **«Открыть»** и **«Редактировать»**.

Для выполненной задачи показывать:

* название;
* дату завершения;
* действие **«Вернуть в работу»**.

Основной экран не должен постоянно показывать полный список задач. Общий список доступен только отдельной кнопкой.

### 4.3. Создание задачи

Форма открывается как bottom sheet на мобильном устройстве и как modal dialog на desktop.

Поля:

* **Название** — обязательное, максимум 200 символов;
* **Описание** — необязательное, максимум 5000 символов.

После создания:

* задача добавляется в конец карусели;
* текущая задача не переключается;
* форма закрывается;
* появляется сообщение **«Задача добавлена»**.

### 4.4. Редактирование задачи

Можно изменить:

* название;
* описание.

История прогресса при редактировании не изменяется.

### 4.5. История прогресса

История открывается внутри карточки или отдельным экраном.

Записи показываются от новых к старым:

* текст записи;
* дата;
* локальное время пользователя.

Редактирование и удаление записей прогресса в MVP не требуется.

---

## 5. Работа с прогрессом

Прогресс задачи — это журнал текстовых записей, а не процент выполнения.

При нажатии **«Записать и дальше»**:

1. Поле прогресса должно содержать хотя бы один непробельный символ.
2. Запись сохраняется в базе.
3. Поле очищается.
4. Текущей становится следующая активная задача.
5. Новая текущая задача сохраняется в пользовательском состоянии.
6. Интерфейс показывает следующую задачу без полной перезагрузки страницы.

Текст записи:

* максимум 5000 символов;
* сохраняется с серверным временем;
* привязан к задаче и пользователю.

Для каждой задачи незаписанный текст хранить локально в `localStorage`.

Ключ черновика должен включать идентификатор задачи. При переключении между задачами незаписанный текст не должен теряться.

После успешного сохранения соответствующий черновик удаляется.

Кнопка **«Пропустить»**:

* не создаёт запись прогресса;
* просто переключает на следующую задачу;
* незаписанный черновик текущей задачи сохраняется локально.

---

## 6. Завершение задачи

При нажатии **«Готово»**:

1. Задача получает статус `completed`.
2. Устанавливается серверное время завершения.
3. Задача сразу исключается из карусели.
4. Открывается следующая активная задача.
5. Показывается toast:

```text
Задача завершена
Отменить
```

Кнопка **«Отменить»** доступна пять секунд и возвращает задачу в активное состояние.

Если завершена последняя активная задача, показать экран:

```text
Все задачи завершены

Добавить новую задачу
Посмотреть выполненные
```

Выполненную задачу можно вернуть в работу через экран выполненных задач. После восстановления она добавляется в конец карусели.

## 7. Логика карусели

Активные задачи сортируются по полю `position` по возрастанию.

Правила:

* новая задача получает позицию после последней активной задачи;
* текущая задача хранится отдельно для каждого пользователя;
* при повторном открытии приложения показывается последняя текущая задача;
* если текущая задача была завершена или отсутствует, выбирается следующая активная;
* если следующей нет, выбирается первая;
* движение назад от первой задачи открывает последнюю;
* пользовательские задачи никогда не смешиваются между аккаунтами.

Перетаскивание и ручная сортировка задач в MVP не требуются.

## 8. Мобильный интерфейс

Приложение проектировать mobile-first.

Поддерживаемые размеры:

* минимальная ширина: 320 px;
* iPhone Safari;
* Android Chrome;
* desktop Safari, Chrome и Firefox.

Требования:

* использовать `100dvh`, а не `100vh`;
* учитывать `safe-area-inset-top` и `safe-area-inset-bottom`;
* нижняя панель действий должна оставаться доступной над системной областью телефона;
* экран не должен иметь горизонтального скролла;
* минимальный размер интерактивной области — 44×44 px;
* поле прогресса должно оставаться видимым при открытии экранной клавиатуры;
* основная кнопка должна быть доступна большим пальцем;
* кнопки не должны располагаться слишком близко друг к другу;
* интерфейс должен корректно работать в portrait и landscape;
* после нажатия кнопки должна сразу появляться визуальная обратная связь;
* во время запроса повторное нажатие блокируется;
* ошибки показываются рядом с действием, а не только в консоли;
* анимация переключения карточки — не более 150 мс;
* учитывать `prefers-reduced-motion`;
* запрещены длинные декоративные анимации.

## 10. Схема базы данных

### Таблица `users`

```sql
CREATE TABLE users (
    email TEXT PRIMARY KEY,
    created_at INTEGER NOT NULL,
    last_seen_at INTEGER NOT NULL
);
```

### Таблица `tasks`

```sql
CREATE TABLE tasks (
    id TEXT PRIMARY KEY,
    user_email TEXT NOT NULL,
    title TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL CHECK (status IN ('active', 'completed')),
    position INTEGER NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    completed_at INTEGER,
    FOREIGN KEY (user_email) REFERENCES users(email) ON DELETE CASCADE
);
```

### Таблица `progress_entries`

```sql
CREATE TABLE progress_entries (
    id TEXT PRIMARY KEY,
    task_id TEXT NOT NULL,
    user_email TEXT NOT NULL,
    note TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    FOREIGN KEY (task_id) REFERENCES tasks(id) ON DELETE CASCADE,
    FOREIGN KEY (user_email) REFERENCES users(email) ON DELETE CASCADE
);
```

### Таблица `user_carousel_state`

```sql
CREATE TABLE user_carousel_state (
    user_email TEXT PRIMARY KEY,
    current_task_id TEXT,
    updated_at INTEGER NOT NULL,
    FOREIGN KEY (user_email) REFERENCES users(email) ON DELETE CASCADE,
    FOREIGN KEY (current_task_id) REFERENCES tasks(id) ON DELETE SET NULL
);
```

### Индексы

```sql
CREATE INDEX idx_tasks_user_status_position
ON tasks(user_email, status, position);

CREATE INDEX idx_progress_task_created
ON progress_entries(task_id, created_at DESC);

CREATE INDEX idx_progress_user_created
ON progress_entries(user_email, created_at DESC);
```

Идентификаторы создавать через:

```ts
crypto.randomUUID()
```

Все временные значения сохранять как Unix timestamp в миллисекундах.

## 11. API

Все API-маршруты начинаются с `/api`.

### Пользователь

```text
GET /api/me
```

Ответ:

```json
{
  "email": "user@example.com"
}
```

### Получить задачи

```text
GET /api/tasks?status=active
GET /api/tasks?status=completed
GET /api/tasks?status=all
```

### Создать задачу

```text
POST /api/tasks
```

Тело:

```json
{
  "title": "Подготовить доклад",
  "description": "Собрать структуру и примеры"
}
```

### Изменить задачу

```text
PATCH /api/tasks/:taskId
```

Тело:

```json
{
  "title": "Подготовить доклад про Kubernetes",
  "description": "Собрать структуру, примеры и демо"
}
```

### Получить текущую задачу карусели

```text
GET /api/carousel/current
```

Ответ:

```json
{
  "task": {
    "id": "f685bf80-b485-4832-9488-040f7f3414b2",
    "title": "Подготовить доклад",
    "description": "Собрать структуру и примеры",
    "lastProgress": {
      "note": "Собрал структуру вступления",
      "createdAt": 1785524400000
    }
  },
  "currentIndex": 1,
  "total": 4
}
```

`currentIndex` возвращать начиная с нуля.

### Переключить карусель

```text
POST /api/carousel/move
```

Тело:

```json
{
  "direction": "next"
}
```

или:

```json
{
  "direction": "previous"
}
```

### Записать прогресс и перейти дальше

```text
POST /api/tasks/:taskId/check-in
```

Тело:

```json
{
  "note": "Закончил первый раздел, дальше начать со схемы архитектуры"
}
```

Ответ должен содержать сохранённую запись и следующую текущую задачу.

### Завершить задачу

```text
POST /api/tasks/:taskId/complete
```

### Вернуть задачу

```text
POST /api/tasks/:taskId/reopen
```

### Получить историю прогресса

```text
GET /api/tasks/:taskId/progress
```

Каждый endpoint обязан проверять, что ресурс принадлежит текущему пользователю.

Нельзя принимать `user_email` от frontend. Email всегда извлекается только из проверенного Access JWT.

## 12. Валидация

### Название задачи

* обязательное;
* после `trim()` не пустое;
* максимум 200 символов.

### Описание

* максимум 5000 символов.

### Запись прогресса

* после `trim()` не пустая;
* максимум 5000 символов.

API должен возвращать единый формат ошибки:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Запись прогресса не может быть пустой"
  }
}
```

Использовать HTTP-коды:

* `200` — успешное чтение или изменение;
* `201` — создание;
* `400` — ошибка входных данных;
* `401` — отсутствует авторизация;
* `403` — недействительный Access JWT;
* `404` — ресурс не найден или принадлежит другому пользователю;
* `409` — конфликт состояния;
* `500` — внутренняя ошибка.

## 13. Безопасность

Обязательно:

* проверять подпись Cloudflare Access JWT;
* проверять `iss`, `aud`, `exp` и `nbf`;
* не доверять email из frontend-запроса;
* использовать только parameterized D1 queries;
* не выводить содержимое JWT в логи;
* не логировать записи прогресса;
* добавить Content Security Policy;
* добавить `X-Content-Type-Options:
